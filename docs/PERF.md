## Что сделано

- **Раскладка** (`LayoutEngine.cs`): разбор длин без аллокаций, кэш чисел и line-height; строки текста без объекта на слово; кэш размеров на блоке (`SizeEntry`, `LastCall`/`LastLayout`); grid — быстрый автоплейсмент; flex — пулы и диапазоны строк вместо LINQ.
- **Инкрементальная раскладка**: `LayoutEngine.Update(changed)` перестраивает только изменившиеся поддеревья; если блок исчезает из потока — родителя целиком. Шаблон сообщает, что менять (`TemplateChanges.Relayout`), `UiWindow` копит `dirtyLayout`. Тест: 1500 случайных изменений, инкрементальный результат совпадает с полным.
- **Шаблон без изменений — 0 Б**: кэш упакованных значений (`Expr.Num`, `Box(bool)`, типизированные геттеры свойств), текст сравнивается с текущим без новой строки, `data-for` с теми же объектами идёт быстрым путём, высота распорок виртуального списка сравнивается числом, а не строкой стиля.
- **Отрисовка — 0 Б**: префаб `<item>` ищется при смене атрибута, а не каждый кадр (`UiControls.itemPrefabs`); `Painter.Probe` раскладывает аллокации отрисовки по частям для самопроверки.
- **Прочее**: таймеры через `Stopwatch.GetTimestamp()`, замечания форматируются только новые, кэш ширин текста и слот шрифта на стиле, обходы дерева без итераторов.

## Наведение мыши на странице с 300 карточками (до A4)

**Метод.**

### Индекс селекторов в каскаде (после B3)

`StyleEngine.Add` раскладывает каждый селектор по одной корзине по его последнему (определяющему) составному селектору: по id, иначе по первому классу, иначе по тегу, иначе в «универсальные». `Resolve(e)` берёт кандидатов: универсальные, корзина тега `e`, корзина id `e`, корзины всех его классов; сортирует их по `order` (порядок исходного цикла) и вызывает тот же `sel.Matches(e)`. Поэтому `matched`, строка ключа кэша и всё дальше те же, что и раньше. Буфер кандидатов один на движок: `Resolve` не вызывает сам себя, лишних аллокаций на элемент нет (`HashSet` классов перебирается структурным перечислителем). Переключатель `internal bool UseIndex` (тесты сравнивают оба режима): `tools/ui_test/StyleIndexTests.cs`, 30 таблиц стилей из `own/*/UI`, около 189 тысяч сравнений Values, Vars и FontSizePx без расхождений.

Замер до и после на одной и той же странице (с `UseIndex = false` и `true`; в это время страница стала больше: 22 932 элемента, 621 правило, поэтому числа выше таблицы B3 не сопоставимы). Debug, один прогон, мс, относительные.

| случай | без индекса | с индексом |
|---|---|---|
| первая печать, 300 карточек, медиана | 1 670,7 | 1 106,9 |
| из них каскад | 1 481,1 | 886,1 |
| resize одной карточки, медиана | 60,2 | 55,6 |
| hover-perf a: указатель входит в окно (полный `Compute`, 6 006 элементов) | 229,0 | 46,3 |
| hover-perf b: карточка 0 -> карточка 1 | 1,62 | 0,29 |

Каскад стал быстрее примерно на 40 процентов, а не на порядок: остаток — не перебор селекторов, а работа `Resolve` на каждом элементе (список `matched`, строка ключа, поиск в кэше). Дальше выигрывает только то, что вообще не перекаскадирует элементы.

### Структурное изменение: перекаскад только затронутого (после индекса)

`TemplateChanges` теперь несёт `Created` (корни созданных элементов: копии data-for, распорки) и `Reshaped` (контейнеры, у которых изменился список детей). `UiWindow.EnsureLayout` вместо `restyleAll` вызывает `Template.RestyleStructure`: каждый новый корень получает стиль со своим поддеревом (родитель уже стилизован, иначе откат на всю страницу), а если какой-то селектор читает позицию среди соседей (`:first-child`, `:last-child`, `:nth-child`), перекаскадируются дети контейнера, которые могут совпасть с таким составным селектором (без учёта позиции). Раскладка при `Structure` остаётся полной. Селекторы `+` и `~` (этап D) должны расширить это на следующих соседей. Тесты: `tools/ui_test/ScopedRestyleTests.cs` (страницы карты, магазина, табменю, сонара и мини-таблицы позиций: все элементы совпадают с полным `Compute` свежего документа).

## Скругление по overflow (2026-11-16): проход в начале кадра, не проверено в игре

Цель: блок с `overflow: hidden|auto|scroll` по обеим осям и `border-radius` режет всё поддерево по скруглению. Первая попытка (лейн F) переключала цель рисования посреди кадра и стирала уже нарисованный фон окна (`ui_host`); эта версия цели посреди кадра не переключает.

**Решение (Core, `Core/RoundedClip.cs`).** `Needs`: блок нуждается в пути, если оба края обрезаются, есть радиус и какой-либо бокс поддерева заходит в угловой квадрат вне дуги (точная проверка, `Reaches`). `Inset` даёт радиусы padding-бокса, `TileAlpha` — покрытие одного текселя угла (дополнение к `Alpha`, тест сверяет), `MaxPerFrame = 32`.

**Проход (Render, `Render/RoundedPass.cs`).**
- `BaroUi.PrePass` (`Api/BaroUi.cs`) вызывается из Harmony-префикса на `GameMain.Draw(GameTime)`. Это первая строка игрового кадра, до любого рисования: `BbePipeline.DrawBegin` только включает таймер. Окно к этому моменту обновлено (`Update` идёт раньше `Draw`), поэтому раскладка и прокрутка уже этого кадра. В `tools/ui_host` тот же вызов (`UiWindow.PrePass`) стоит после `Update` и до переключения на цель хоста.
- Проход обходит окно тем же размещением, что и `Paint` (`ScreenMap.Place`, липкость, шаг прокрутки), и собирает блоки в пост-порядке (дети раньше родителя): внутренний блок готов раньше внешнего, в цель которого попадает.
- Для каждого блока: цель `RenderTarget2D` размером padding-бокса (`TextureCache<Element>` в бюджете окна, graveyard при освобождении, повторно используется, пока размер тот же); дети рисуются в координаты цели (сдвиг на -pad) в очищенную прозрачную цель; затем по четырём угловым квадратам цель умножается на покрытие внутренности дуги (плитки `RoundedClip.TileAlpha`, блендинг `Zero`/`SourceAlpha`). Маска запечена в цель, поэтому шейдер и альфа-блендинг на backbuffer не нужны.
- Переключение цели: цель, вьюпорт и scissor устройства сохраняются и восстанавливаются. Если цель уже стоит чужая, проход на кадр пропускается (с сообщением).
- Рисование (`Paint`): вместо детей блока рисуется цель одним спрайтом на место padding-бокса. Цель хранит цвет, умноженный на альфу (так работает батч), поэтому композиция — `One`/`InverseSourceAlpha`, а не `AlphaBlend` батча: иначе цвет дважды умножался бы на альфу. Так нашлось по пиксельному сравнению полупрозрачной пилюли.
- Канвасы и IME-прямоугольник, записанные во время прохода, переводятся в экранные координаты (`Painter.Abs`), чтобы мышь и IME работали по раскладке.
- Попадания (`Hit`) не меняются: считаются по раскладке, не по текстуре.

**Ограничения.** Блок внутри `scale` не получает цель (прямоугольная обрезка; его поддерево считается одним прямоугольником для соседей). Текст самого блока (не детей) дугой не режется. Больше 32 блоков в окне за кадр — прямоугольник и диагностика. Выключатель для сравнения: `BAROUI_ROUNDED=0` (проход не работает, всё как раньше).

**Задержка содержимого.** Проход идёт после обновления и раскладки того же кадра, поэтому содержимое не отстаёт на кадр. Отстаёт только то, что меняется во время `Draw`.

**Стоимость (не измерена в игре).** Обход окна выполняется каждый кадр, пока в окне есть блок с радиусом и обрезкой по обеим осям. Обход повторяет обход `Paint` по боксам. Поэтому на странице без такого блока обход всё равно идёт (он ничего не рисует, но нулевой стоимости нет). Кэш «по раскладке» не сделан: решение зависит от прокрутки, которая меняется без раскладки. Аллокации в установившемся кадре не измерялись.

**Проверка на `tools/ui_host`:**
- `own/BaroUI_Example/UI/example.html`, 1600x900, 90 кадров. До: углы списка «Отсеки» квадратные (строка и заголовок выходят за дугу); после: дуга 12u у всех четырёх углов, остальные пиксели страницы без изменений (различие только в углах списка и концах полос батарей). Пилюли внутри списка совпадают с базовым кадром (`(23,46,42)` против `(24,46,42)`, предупреждение `(50,47,33)` точно).

- Картинки (`<img>` и `url()`) в `ui_host` не выводятся ни до, ни после изменения (проверено и с `BAROUI_ROUNDED=0`), поэтому картинка в скруглённой карточке не проверена; проверен тот же путь (ребёнок, заходящий в угол).

## Псевдоэлементы и :has() (лане D): цена

**Модель.**
- Страница без `::before`/`::after`: `hasPseudo` ложно, в `ResolveOne` ничего лишнего, коробок нет. Со стилем: на каждый перестилаемый элемент два вызова `Resolve` для `::before` и `::after` (тот же индекс правил, кэш стилей по родителю; промах только при первом появлении набора правил) и, если текст не поменялся, без новых объектов. Новый текст (например `attr()` после смены атрибута) — один `ComputedStyle` копией (`CloneBare`) и один `TextNode`; это единственная аллокация, и она только на перестиле, не в спокойном кадре. Коробка — отдельный `Element` на элемент, создаётся при первом перестиле такого элемента; в `Children` не входит.
- Перестил коробки: `UiWindow.Collect` берёт коробки вместе с элементом, поэтому смена только `content` или стиля коробки даёт тот же проход `AffectsLayout`, что и смена элемента (текст лежит в значениях стиля, `-bbe-content-text`).
- Страница без `:has()`: `hasDeps` пуст, `ComputeHas`/`HasCore` выходят сразу, `ComputeStateCore` добавляет одну проверку счётчика. Замер ниже совпадает с таблицей выше (а, б, в, г: 0 перестилок по состоянию).
- Страница с `:has()`: при изменении `e` (класс, атрибут, состояние, состав) якорями считаются предки `e` и предыдущие братья каждого из `e` и его предков (`StyleEngine.AnchorsOf`, число ~ глубина + число предыдущих братьев на пути). Якорь берётся, если его составной селектор с `:has()` проходит `MatchesIgnoringState` (состояния и `:has` там не проверяются, это надмножество). Перестил: если `:has()` стоит в последнем составном — один `Refresh` якоря (он сам и его наследники, если наследуемое изменилось); иначе `ComputeTree` якоря, с `+`/`~` в хвосте — ещё и его последующих братьев.
- Цена проверки `:has()`: `Selector.AnyRelative` обходит область: потомков (для пробела), детей (`>`), следующего брата (`+`) или следующих братьев (`~`) с их поддеревьями, если в относительном селекторе больше одного составного. Значит одна проверка стоит O(поддерево якоря) в худшем случае: `.map:has(.x)` над контейнером в 6000 элементов проверяет до 6000 узлов при каждом перестиле контейнера. Это главное ограничение; для больших контейнеров лучше `:has(> .x)` (только дети) или правило на сам элемент.
- Состояния внутри `:has()` (`:has(:hover)`) не попадают в индекс состояний `stateDeps` (он для элемента и его предков по селектору), а идут через `hasDeps` с битами `HasBits()`: наведение на потомка перестилает якорей, не всю страницу.

**Замеры** (`tools/ui_test`, Debug, этот прогон, числа относительные).

| что | до (без :has в этом листе) | после (с :has) |
|---|---|---|
| hover-perf, `ComputeState`: вход в окно / уход (страница 6 006 элементов, 300 карточек) | 0,017 мс, 0 элементов | — (тот же лист, без `:has`) |
| hover-perf, `ComputeState`: карточка 0 → карточка 1 | 0,011 мс, 0 элементов | — |
| hover-perf, полный набор | 17 из 17 | — |
| map-perf, полный набор (18 проверок) | 18 из 18 | — |
| pseudo/has perf: наведение на ребёнка одной из 300 карточек (лист карточек с `:has(:hover)` и `:has(.hot)`) | 0,002 мс, 1 элемент | 0,025 мс, 22 элемента |

Кэш и аллокации: `AnchorsOf` и `HasCore` берут один общий список (`anchorBuf`) и не выделяют память в спокойном кадре; сравнение `into.Contains` линейное, оно короткое (число якорей невелико).

**Не проверено:** перерисовка в игре (`Render/` не компилируется в тестах: проверен только `cscheck`), попадание мыши на коробки (`Painter.Hit` возвращает элемент-владелец: проверено чтением кода, не тестом), страница из `own/BBE_Mods` с `:has()` в живом окне.
